# Fugue DNS / edge 故障转移修复方案

日期：2026-10-12。状态：供审阅，尚未实施或发布。

依据：[线上调查与复现证据](bwg-edge-failover-investigation-20261012.md)。本方案承接已确认的缺陷，不将 BWG、DMIT 的预期离线当作需要修复的主机故障，也不推断缺失的历史流量数据。

## 目标与边界

一个物理 edge 失联后，Fugue 应自动停止向它分配新的合格 DNS 答案，继续使用满足原有地域、路由、身份和证明要求的其他 edge。某条记录没有合格入口时，该记录失败，不能连带撤下整个有效 DNS listener。

分两个阶段完成：第一阶段修复本次已证实的故障隔离与公共入口问题；第二阶段补齐长期离线管理和可验证的故障转移观测。第一阶段不能依赖人工提前声明 BWG 离线，必须同样处理突然断网。

保持以下约束：

- 配置意图、约束策略、签名不可变产物、运行时事实、执行代码分别管理。代码升级本身不改变 DNS 选址策略、地域限制、quorum 或公共入口归属。
- 无效候选不得覆盖仍有效的正向 LKG；保留 LKG 不等于保留过期、撤销或身份不匹配的路由证明。读取缓存、重启和探测失败均不得延长任何原始有效期。
- 不修改 Argus 应用，不重启业务 Pod，不变更 SSH 主机身份、known_hosts、密钥或备份，不恢复 BWG/DMIT 网络。
- 所有生产变更通过 `main` 和 `.github/workflows/ci.yml`。代码候选部署与流量配置切换分开验收；禁止手工修改 iptables、Deployment 或直接删除旧 Pod 代替修复。
- DNS 控制新解析产生的连接；它不能迁移已经连接到失联 edge 的 TCP 会话，也不能保证外部递归解析器立即清除缓存。

## 第一阶段：恢复正确的故障隔离

### 1. 保留探测的原始原因，给修复建立证据链

已确认：`platform_serving.go` 的 release 检查把空证明的 `not_observed`、`probe_unavailable` 等原因覆盖为 `traffic_release_mismatch`。

修改 `internal/dnsserver/platform_readiness.go`、`internal/dnsserver/platform_serving.go` 及对应的运行时状态输出：

1. 分开记录“采集是否开始及其结果”和“证明校验结果”。无证明时不伪造版本不匹配；实际携带错误 release 的证明继续拒绝。
2. 每轮生成可关联的观察 ID，记录计划 digest、开始/结束时间、截止时间、排队/开始/成功/失败/未调度数量，以及按物理入口聚合的预算消耗。
3. 将 DNS 决策与实际使用的观察及证明关联。记录错误分类、对象 ID 和时间，不记录认证内容或业务响应。
4. 指标使用有界分类；详细对象关联进入有界审计。记录队列丢弃量，避免把“没有保存回执”解释为“没有发生请求”。诊断写入不得阻塞 DNS 查询。

这是第一阶段修复的一部分，不需要为了取得这些指标额外先发布一次不恢复服务的版本。新增对外字段遵循 OpenAPI-first；兼容已有消费者，不悄悄改变旧字段含义。

### 2. 分离正向配置身份、记录健康和 listener 就绪

已确认：同一 assignment 的负面记录观察会清除 `record.Positive`，导致 `/readyz` 503，进而撤下公共 Service 的整个端点；此时 NS 和部分正常记录仍然能够回答。

修改 `internal/dnsserver/platform_serving.go`、`internal/dnsserver/listener_readiness.go`，并检查刷新、候选切换和恢复路径：

| 状态 | 含义 | 允许的行为 |
| --- | --- | --- |
| 已验证配置 | 已接纳的签名配置、assignment、授权及原始有效期限 | 在原有有效边界内保留，不因单条探测失败被改成“从未验证” |
| 记录当前可服务性 | 该记录的合格证明和 quorum | 独立更新；不足时仅该记录 SERVFAIL，不返回不合格地址 |
| listener 就绪 | 有效配置与实际 UDP/TCP listener 可用 | 不要求所有动态记录同时健康；不能让未验证或过期配置通过 |
| 候选发布验收 | 新版本是否满足完整切换要求 | 继续使用严格门槛，不能以 listener Ready 代替 |

同一已接纳 release 的记录降级，只更新运行时 facts 和降级状态，保留原正向配置身份及有效期限。新的、未通过验收的候选不能获得这一待遇。实现必须覆盖刷新失败、assignment 并发变化、source transition、重启和撤销路径，不是简单移除 `/readyz` 中的 `Positive` 检查。

重启后仍重新获取运行时证明，不能把磁盘 checkpoint 中的历史记录健康当作新观察。全量记录健康继续独立上报，避免修复后所有看板只显示“Ready”而掩盖局部失败。

### 3. 让探测公平推进，限制单个失联入口的消耗

已确认：collector 每轮都从计划索引 0 开始，所有物理入口竞争同一个并发池；本机调用真实实现，连续两轮均复现后段健康目标一次也未被调用。

修改 `internal/dnsserver/platform_readiness.go` 的调度器，并将生产 serving 和候选观察接入一致的调度规则：

1. 按已验证计划中的物理连接目标划分队列，在全局并发上限内限制单目标的占用，让多个入口获得轮转机会。连接目标分组只用于资源隔离，不赋予任何路由成功状态。
2. 同一计划跨轮保存轮转进度和最后尝试时间；结合证明剩余寿命安排刷新，同时保证从未探测的目标也能推进。不能每轮重置为固定队头。
3. 为持续连接失败的入口设置有界退避和恢复探测预算。仅连接层面的共同故障可以影响该连接目标的调度；单 hostname 的路由、TLS 或版本错误不能被泛化为全部路由失败。
4. 每个 hostname/path/edge 仍须取得自身匹配的证明。某个入口的一次成功只解除连接退避，不能让它承载的所有记录直接变成 Ready。
5. 调度状态绑定计划和 assignment，限制数量与生命周期；计划切换后不串用旧事实。保留现有被允许的短暂刷新失败处理及原始证明截止时间，硬性撤销、错误绑定不得被成功缓存掩盖。
6. 若签名策略给出的并发、时限与实际负载无法完成必要刷新，明确报告预算不足。阈值调整走独立策略发布，不能通过延长证明有效期、降低 quorum 或无限加并发掩盖容量问题。

### 4. 统一公网 DNS 端口所有权

已确认：两地公网请求曾实际进入旧 hostPort Pod 并收到 SERVFAIL；新 Service 端点退出 Ready 后，旧进程仍拥有可接收公共流量的路径。旧进程 checkpoint 已过期，不能作为回退目标。

围绕 `scripts/reconcile_dns_transport.py`、DNS 运行时部署声明和 `deploy/environments/production/dns-transport/transport.json` 完成独立改进：

1. 声明式盘点每个 `公网 IP + UDP/TCP + 53` 的 Service、hostPort、hostNetwork 及实际转发所有者；发布前拒绝未声明的重叠接收路径。仅确认 Service selector 正确不算验收通过。
2. 以现有声明式 DNS transport 为公共新流量的唯一管理入口。旧 executor 的保留与公共端口接收权分开管理，避免 Service 无 Ready endpoint 时隐式进入过期旧进程。
3. 新候选先经现有验证入口及直接目标验证：签名、assignment、有效期限、全量记录要求、UDP/TCP 响应和真实接收实例全部通过，再单独切换公共入口。
4. 通过正常 CI 执行旧端口接收权的有序交接。若旧 hostPort 的释放必须替换旧 DNS Pod，先完成 DNS 流量交接、连接排空与身份材料保留的专门验收；不能把“不重启业务 Pod”误写成“任何 DNS 旧进程永远不能退出”。
5. 验证空端点场景不会回落到未授权旧实例。故障注入只在隔离环境；生产用只读所有权核对和有界查询确认。

现有正常 handoff 对旧端和新端都有严格要求。若旧端已经过期，不能为了切换而伪造旧端 Ready 或放宽正常 handoff 校验；需要在独立配置流程中明确表示“恢复接管”，提供当前配置权威、目标完整正向验收、端口所有权和防并发修改证据。它不接受过期旧端作为正向证明，也不把旧端设置成回退目标。

具体旧端口释放动作须由上述只读盘点确定，再形成可审阅的配置 diff。现有 `dns_selector_retirement` lane 是选择算法退役流程，不能仅凭名称把它当作 hostPort 清退流程。

## 第二阶段：长期离线和状态口径

### 5. 通用的长期离线声明与恢复条件

在配置意图中表达节点计划暂停参与新流量、原因及预计恢复时间，通过独立配置发布生效；不在代码中匹配 BWG、DMIT 或特定日期。运行时仍单独维护心跳、可达性、worker ACK、路由证明和实际可服务状态。

用户给出的 2026-10-18 仅作为 BWG 的预计恢复提示。到期不能自动认定它健康；重新加入需要实际连接成功、身份匹配、有效当前路由/TLS 证明和受控观察窗口。心跳恢复也不足以证明所有路由已可服务。

固定节点的 SSH front 在长期离线期间出现 Pending/terminating 对象积累，这一现象已确认，但尚不足以确定每一次替换的控制器触发链。先补齐对象 owner、节点状态、reconcile ID、触发条件和创建结果的关联，并在隔离环境复现。只有锁定触发路径后才实现有界重试、幂等创建和等待节点恢复的调谐状态；不能仅凭现象强删对象、卷或密钥。

计划离线声明是运维能力，不是第一阶段自动故障转移的前提。调谐必须仍能处理事先未声明的断网。

### 6. 明确“允许使用”与“现在能服务”的区别

统一节点列表、详情、desired-state、traffic-safety 和 route explain 的语义，提供可对照的状态：

- 配置/策略是否允许参与；
- 观察来源、时间、新鲜度与拒绝原因；
- 当前有效资格及其证据；
- 当前发布的 ACK、实际装载 digest 和公共入口验证结果。

不把持久化的 `healthy=true` 或策略 `dns_eligible=true` 显示成实时可服务，不把 traffic-safety 的可选入口检查显示成公网 DNS 已恢复。对外契约先改 `openapi/openapi.yaml`，生成后端产物并同步前端契约与消费代码；旧字段保持兼容并明确其语义。

增加故障转移时间线：首次失败观察、最后合格证明到期、最后包含失联入口的权威答案、首次备用正向答案、对应 TTL、抽样递归答案和入口接收计数。报告数据覆盖范围和丢弃量，不用抽样值冒充全量客户端流量比例。

## 验收矩阵

使用中性合成记录和隔离环境。不能向真实 BWG 或业务节点注入断网、删除 Endpoint、撤销密钥来验收。

| 场景 | 必须通过的断言 |
| --- | --- |
| 调度压力 | 671 条合成探测，其中 171 条共享一个黑洞入口，其余分布在三个健康入口；8 并发、30 秒观察预算、5 秒单探测上限下，健康模拟响应不超过 200 ms 时，所有健康探测在一轮内至少完成一次；连续多轮位置靠后的目标不饥饿 |
| 超预算与恢复 | 多入口同时慢、全部入口失败、计划扩大和退避恢复均有界；如无法满足刷新目标，报告明确预算不足，不伪造成功或延长证明 |
| 完整状态链 | 从正向配置经过真实 sync 得到部分负面事实后，正常记录及 NS/SOA 仍可回答，listener 保持合法就绪，失败记录严格拒绝 |
| 新候选与身份 | 新候选未通过、签名错误、tenant/route/release/edge 绑定不匹配、回放及撤销仍拒绝；候选失败不破坏原有效正向配置 |
| 有效期与重启 | 控制面短暂不可达、进程重启、checkpoint/证明到期时不续造权威；相同缓存重复读取不能延长有效期 |
| 地域与 quorum | 遵守原有地域限制和最小健康入口数；不能用策略不允许的地区或单个证明替代多个所需入口 |
| 公共端口 | UDP/TCP 均到声明目标；无 Ready endpoint 时不进入旧过期 hostPort；存在所有权冲突、过期目标或实例变化时拒绝不安全交接 |
| 独立恢复 | 代码构建失败不撤销既有产物；配置切换失败保留原合法入口；旧端过期的恢复接管与正常 handoff 分别测试 |
| 预期离线 | 长时间离线对象数量和重试频率有界；日期到达不自动放流；恢复必须重新获得实际有效证明；身份材料完整保留 |

30 秒是上述受控负载下的调度验收目标，不是对所有网络或所有客户端的恢复时间承诺。线上报告应区分探测、权威答案、TTL/递归缓存和已有连接四段时间。

运行受影响 Go 包测试及竞态测试、DNS transport 的 Python 测试与相关配置验证。API 变化额外要求 `make generate-openapi`、`make test`，随后前端 `openapi:sync`、`openapi:generate`、`contract:check`。测试失败不绕过检查发布。

## 发布与回退顺序

1. 发布前重新核对远端 main、最新 CI、线上实际镜像与配置 generation，冻结本次验收基线；不得使用调查时记录的旧版本强行覆盖后续合法发布。
2. 将最小诊断修复、状态解耦、调度修复分成可独立审阅的提交；完成隔离测试后，通过正常 CI 构建并部署未接收公共流量的 DNS 候选。使用现有权威兼容的产物，不顺带改选址权重、期限和 quorum。
3. 候选通过完整验收后，单独形成端口所有权与恢复接管的配置变更；先一地、验收通过后再另一地。每一步重新验证目标实例、配置 digest、证明和有效期限，防止验收期间版本已变化。
4. 每地同时检查公网 UDP/TCP、关键记录与普通合成记录、A/AAAA/NS/SOA 的预期结果、实际接收实例、错误分类、队列覆盖率及 CPU/内存/连接数。AAAA 等原本不存在的记录按其正确 DNS 语义验收，不能要求一律返回地址。
5. 正确故障转移稳定后再发布第二阶段的长期离线与状态口径变更，避免紧急恢复与全平台生命周期改造混在一起。

任一步发现证明错误、公共流量进入错误实例、无关记录回归、资源持续异常或业务出现相关回归，停止扩大范围并保留关联证据。回退只能指向仍经验证且未过期的正向目标；若没有这样的目标，应明确“无安全回退目标”，保留尚可服务的合法状态并走恢复流程，不能转回已知过期旧 Pod。

生产验收不以“GitHub Actions 绿色”或“Pod Running”结束。完成标准是：实际公网答案与签名策略一致，失联 edge 在其证据失效后不再进入新答案，合格备用 edge 持续可选，不相关记录可用，公共端口所有权唯一，错误原因可追溯，并且业务与 SSH 身份材料未被改动。
