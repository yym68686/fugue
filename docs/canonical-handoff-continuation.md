# Continuing a safe rollout during canonical drain

A promoted independent revision can receive new connections through the canonical Service while the original canonical Deployment retains long-running connections. The original cohort must not be terminated merely because a later release is promoted.

The handoff annotation retains the original Deployment UID, release key, image and source release ID. Its traffic target may advance only to the current 100% stable release whose durable rollback predecessor is the recorded target. Both revisions must have immutable workload bindings. The controller verifies the destination's health, exact Service identity and fresh edge publication before changing the canonical Service selector with UID, resource-version and selector tests.

`source_release_id` remains unchanged across promotions. `previous_target_release_id` permits recovery if a process stops after persisting the new target but before replacing the Service selector. A previous revision cannot retire or have resources removed while a managed canonical Service still selects it. It must also pass the existing positive connection-drain and current traffic-proof checks.

If the preceding pass already replaced the canonical Deployment but did not restore its Service, only the exact preceding promoted executable snapshot can establish the next drain cohort. Rendering that snapshot with observed scheduling must reproduce the live release key and image; the complete Pod cohort still undergoes ordinary drain validation.

After the controller verifies that all managed canonical Service endpoints point exclusively at the independently serving revision, it records a ten-minute deadline on the canonical Deployment. Retries, controller restarts, and later promotions do not extend an already withdrawn cohort's deadline. A handoff from an older controller without a deadline starts its budget on the first verified withdrawal observation after upgrade; a different source cohort starts a new budget.

The controller lets connections finish naturally, then starts graceful termination when the cohort has been quiet, or within the last minute of the budget if the connection-aware native sidecar can finish the drain. Without the verified hook, a busy cohort is not stopped early. It revalidates traffic, target readiness, workload ownership and source identity, atomically checkpoints the stop and scales only the withdrawn Deployment to zero, then sends UID-preconditioned graceful Pod deletion requests using the remaining budget. The Pod's preStop does not receive a second ten minutes. A targeted leader sweep resumes due checkpoints without relying on a live deployment operation. The canonical replacement is applied only after the old cohort has actually disappeared and scale-down is observed. If traffic proof is missing or the node or Kubernetes API cannot complete termination, the controller keeps the handoff pending rather than treating elapsed wall time as proof of a safe stop.

An incomplete canonical drain does not prevent independent cleanup of other withdrawn revisions. Active operations, grace and rollback windows, immutable identities, traffic references, endpoint evidence and positive drain observations continue to govern that separate cleanup. The canonical deadline is not permission to delete an independent release by timeout.

A deployment operation that changes only an already-enabled safe-rollout policy may commit that policy when canonical convergence is pending. Its full remaining desired spec must match the current stored spec, and it must not change deployment source. Mixed image, environment, storage, replica or other runtime changes cannot use this path. The managed desired-state projection is written before the pending handoff is returned; background reconciliation continues to enforce the same drain and readiness guards.
